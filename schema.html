Linked Data Context

Interoperability

This field lets the schema speak the same language as other cultural heritage databases worldwide — connecting our records to shared vocabularies and authority files without changing how the data looks to developers.

What this field does

A pointer to a shared vocabulary document that maps our field names onto internationally recognised terms used by museums, libraries, and archives. Adding this turns our JSON records into Linked Open Data — meaning other institutions can automatically understand and connect to them — without changing how the data looks or works in practice. Think of it as a translation key that runs quietly in the background.

Why Linked Art? The example URI points to the Linked Art vocabulary because it is the closest fit to what this schema describes: physical cultural heritage objects with agents, dates, and spatial annotations, expressed in JSON-LD. Linked Art is built on the CIDOC-CRM museum standard but deliberately simplified — it trades some expressivity for practicality, and it has been validated at scale on photographic archives (the PIA project at Basel processed 53,000+ photographs using it). It is also actively maintained by a community that includes major museums and libraries.

This is not the only option. The @context field is just a URI — swapping it changes nothing else in the schema. Four alternatives worth considering, depending on your priorities:

Dublin Core (dc: / dcterms:)
The most widely understood vocabulary in libraries and archives. Very broad and not object-specific, but maximises interoperability with catalogue systems. Best choice if the primary audience is library discovery platforms rather than museum systems.
dublincore.org/specifications/dublin-core/dcmi-terms/
Schema.org
Google, Bing, and other search engines read Schema.org natively — using it makes records directly indexable and discoverable via web search without any further configuration. Less expressive for complex object description, but by far the easiest path to public discoverability.
schema.org/Photograph
CIDOC-CRM (raw)
The full museum ontology that Linked Art is derived from. More expressive and more precise, but significantly more complex to implement — field names become URIs like crm:E22_Human-Made_Object. Worth considering if the end goal is full RDF triple-store integration.
cidoc-crm.org
Records in Contexts (RiC)
The International Council on Archives' new standard, designed specifically for archival collections rather than museum objects. Better models the provenance chains and custody records that press photograph archives accumulate over time. Still maturing but gaining adoption in national archives.
ica.org/standards/RiC/RiC-O_1-1.html

A pragmatic middle path — used by the PIA project — is a custom minimal context that maps only the most important fields (object identifier, people, dates, locations) onto their equivalents in two or three vocabularies simultaneously. This gives interoperability where it counts without requiring the full overhead of any single standard.

"@context": "https://linked.art/ns/v1/linked-art.json"
"@context": "https://linked.art/ns/v1/linked-art.json"
// Minimal custom context mapping key fields to
// Dublin Core + Linked Art simultaneously
"@context": {
  "dc":         "http://purl.org/dc/elements/1.1/",
  "la":         "https://linked.art/ns/terms/",
  "object_number": "dc:identifier",
  "people":      "la:carried_out_by",
  "locations":   "la:took_place_at",
  "dates":       "dc:date"
}

Object Identity

Required

The basic identifying information for each photograph — its accession number, where it is held, and which institution assigned that number.

What this field does

The photograph's reference number (for example 1983-5116/42460 stamped in the top-right corner). In v4, each piece of information extracted by the model now travels with a short record of how confident we are in it and where it came from — so a reviewer can immediately see whether a number was read from a clear stamp or guessed from a partially obscured mark.

"object_number": {
  "value": "reference number string",
  "source": "description of where on the back it appears",
  "confidence": 0.0–1.0,
  "uncertainty": { ...uncertainty_block... },
  "provenance": { ...provenance_chain... }
}
"object_number": {
  "value": "1983-5116/42460",
  "source": "handwritten, top-right corner",
  "confidence": 0.95,
  "uncertainty": {
    "uncertainty_type": "precise",
    "evidence_basis": "explicit_text"
  },
  "provenance": {
    "source_region": "top-right corner",
    "extraction_method": "direct_transcription",
    "agent": { "type": "software", "id": "claude-sonnet-4-20250514" },
    "timestamp": "2025-03-14T09:22:41Z"
  }
}

Visual Structure

Required

A description of the physical layout of the photograph's back — what types of text and marking appear on it, and how those markings layer on top of one another over time.

What this field does

A list of the physical elements found on the photograph back — caption stickers, rubber stamps, handwritten notes, article cuttings, and so on. In v4, each element can optionally carry a precise spatial reference so that a viewer displaying the photograph alongside its metadata can highlight exactly which part of the image a piece of text came from. This follows the approach used by the PIA project at the University of Basel, which served over 180,000 machine-generated annotations this way.

"components": [
  {
    "component_type": "caption_sticker" | "rubber_stamp"
                    | "handwritten_note" | "printed_label"
                    | "article_cutting" | "other",
    "position": "description of physical location on back",
    "web_annotation": { ...web_annotation_target... },
    "confidence": 0.0–1.0
  }
]

// rubber stamp in centre, handwritten pencil note below
"components": [

  },
  {
    "component_type": "rubber_stamp",

    "confidence": 0.96
  },
  {

What this field does

A photograph back is rarely written all at once — a typed caption might be the original; a rubber stamp and a handwritten date could have been added years later by a picture library. This field records those strata in order, helping us understand when different pieces of information were added, and by whom. Each layer now includes the same uncertainty and provenance records as other fields.

"annotation_layers": [
  {
    "layer_index": 0,
    "layer_type": "caption_sticker" | "rubber_stamp"
                  | "handwritten_annotation" | "printed_label",
    "temporal_order": "first" | "subsequent" | "unknown",
    "estimated_date": { ...timespan... },
    "uncertainty": { ...uncertainty_block... },
    "provenance": { ...provenance_chain... }
  }
]

// agency stamp (same period), pencil note added later
"annotation_layers": [

Content Information

Required

The descriptive heart of the record — the photograph's title, the dates connected to it, and a written description of what it shows. The dates field has been substantially reworked in v4.

What this field does

Press photograph backs carry several kinds of date — when the picture was taken, when it was published, when an agency received it. In v3, each date was stored as a single string plus a flag saying whether it was ambiguous. In v4, dates are stored as ranges with an earliest possible and a latest possible bound, so a vague date like "circa January 1936" can be recorded honestly rather than forced into false precision. The display date for human readers is stored separately. Dates are also now explicitly typed — a stamp date, a publication date, and a caption annotation date are kept distinct.

  "end_of_the_end":   "1936-01-19",
  "display_date":      "19 January 1936"
},
"original_text": "19 Jan 1936",
"type": "stamp_date"

What this field does

The written descriptions of the photograph — one focused on historical context, one on what is visually present. In v4, the contextual description field carries a guidance note based on Harvard archival guidelines: where a person's identity cannot be confirmed from the caption text, the description should record what we can see them doing rather than asserting who they are. This matters because AI models can confidently misidentify people, and those misidentifications can be harmful.

"description": {
  "contextual": "Historical narrative description",
  "visual":      "Description of what is visible in the image",
  "language":    "en",
  "provenance":  { ...provenance_chain... }
}
// Contextual description avoids asserting identity where
// caption text is ambiguous; visual description is neutral
"description": {
  "contextual": "A woman is shown working at a traditional
    basket-weaving frame, identified in the caption as
    Mrs Stott. The setting appears to be an indoor
    workshop or demonstration space, circa 1936.",
  "visual": "A woman in dark clothing seated at a large
    wicker frame. Several completed baskets are
    visible in the background.",
  "language": "en"
}

Entities

People · Organisations · Locations · Events

Everyone and everything named on the photograph back — people, organisations, places, and events. In v4, all entity types gain the ability to link out to multiple international authority files simultaneously, and each link records how confident we are in the match.

What this field does

Records people named or visible in the photograph record. The key change in v4 is that the single authority_uri string — which could only point to one database — has been replaced by a list of authority links, so we can simultaneously record a match in VIAF, Wikidata, and the Library of Congress Name Authority File if all three are relevant. Each link records how confident we are and how the match was made. A new identity_description_note field is available for cases where we can describe a person's role but cannot confirm their name from the source material.

"people": [
  {
    "name": "name as it appears in source",
    "type": "individual" | "group",
    "occupation": "occupation if stated",
    "role_in_image": "subject" | "photographer" | "mentioned_only",
    "identity_description_note": "description if identity unconfirmed",
    "authority_links": [{ ...authority_link... }],
    "confidence": 0.0–1.0,
    "uncertainty": { ...uncertainty_block... },
    "provenance": { ...provenance_chain... }
  }
]

Stamps

Spatial Annotations

Rubber stamps are among the most information-rich features of a press photograph back — they often record agency addresses, dates of receipt, and publication instructions. In v4 they gain a standard web-annotation wrapper so they can be displayed as interactive overlays in image viewers.

What this field does

Records every stamp found on the photograph back with its text, organisation, ink colour, position, and legibility rating. The pixel bounding box (retained from v3) locates the stamp precisely within the scan. New in v4: a web_annotation block wraps this spatial information in the W3C Web Annotation standard, so the stamp region can be highlighted as a clickable overlay in any IIIF-compatible image viewer. Date fields have moved to the fuzzy date-range model.

Sensitivity & Community Governance

Major change in v4

The most significant structural change in v4. In v3, potentially harmful content was recorded with a single yes/no flag. Reparative description scholarship is unambiguous that this is not enough: harm in historical records is multidimensional, specific, and needs to be attributed to its source. A new community governance block also addresses the ethical requirements for materials relating to particular communities.

What this field does

Replaces the v3 contains_harmful_language boolean with a structured list, where each entry records: what category of harm is present (racist terminology, colonial framing, valorising language, information omission, and six others from the A4BLiP / NARA frameworks); crucially, where the language came from — the original 1930s caption, a legacy archivist's description, or the AI model itself; the specific term or phrase; a preferred alternative from the NARA vocabulary; and a contextualisation note for public display. The old boolean is kept as a quick routing flag but is deprecated for any detailed use. A 2025 study processing 7.9 million heritage records identified information omissions — descriptions that simply do not record that a marginalised community is present — as a distinct and under-recognised form of harm, which is why that category is included here.

"harm_assessments": [
  {
    "harm_category": "racist_terminology" | "colonial_framing"
                    | "valorising_language" | "information_omission"
                    | "misgendering" | "dehumanising_language"
                    | "privacy_violation" | "other",
    "harm_source": "original_material" | "legacy_description"
                  | "llm_extraction" | "unknown",
    "offending_term_or_phrase": "exact term",
    "location_in_record": "field path",

What this field does

An entirely new block that sits alongside sensitivity and addresses materials that relate to specific communities who have an interest in how they are described. It provides space for Local Contexts TK Labels — a recognised framework for marking materials with cultural protocols — a link to a feedback mechanism so community members can submit corrections, a record of whether consent for automated description has been obtained, and a separate community review status that is distinct from the internal human review record. This block implements the CARE Principles (Collective Benefit, Authority to Control, Responsibility, Ethics) developed for Indigenous data governance but increasingly relevant across all heritage collections.

  "communities_of_interest": ["community name"],
  "local_contexts_labels": ["TK Label URI"],
  "consent_for_ai_description": "obtained" | "not_required"

  "community_review_status": "not_required" | "pending"
                             | "in_progress" | "approved" | "flagged",
  "feedback_uri": "URI for community feedback mechanism",

Revised

Signals that route records to the right review queue. In v4 these have been upgraded from simple yes/no switches to a more informative system that tells reviewers not just that something needs attention, but why and how urgently.

What this field does

Key additions: a review_priority field (urgent / standard / low / none) tells the review team which records need attention first — urgent for harmful language or possible identity misattribution, standard for date ambiguity, low for minor transcription uncertainties. A review_reason_codes array gives machine-readable reasons that can be used to analyse patterns across batches. The low_confidence_fields list has been upgraded from a plain list of field names to a structured record that includes both the raw model confidence and a separately calibrated confidence score — because research shows AI models are systematically overconfident, particularly for obscure historical figures, and the two numbers should not be conflated.

      "calibrated_confidence": 0.0–1.0,

Raw Text

Revised
What this field does

The full transcription of everything written on the photograph back, plus a segmented version that breaks the text into named parts. In v4, two new fields record the overall transcription quality (high / medium / low) and an estimated character error rate. This matters because research from the Living with Machines project found that named-entity recognition accuracy drops by around 24 percentage points when the underlying transcription quality moves from good to poor — poor transcription quality directly degrades every downstream field that depends on reading a name or date correctly.

"raw_text": {
  "full_transcription": "complete verbatim text from back",
  "transcription_quality": "high" | "medium" | "low",
  "character_error_rate_estimate": 0.0–1.0,
  "segments": [
    {
      "segment_type": "caption" | "stamp_text" | "handwritten_note"
                     | "printed_label" | "other",
      "text": "verbatim segment text",
      "web_annotation": { ...web_annotation_target... }
    }
  ]
}

Evaluation Metadata

New block
What this field does

A new block that records how well the extraction actually performed on this record, when that information is available. It links the record to a batch extraction run so quality statistics can be aggregated; flags whether a human-verified ground-truth version of the record exists for comparison; records field-level accuracy scores; and notes any fields where the model is suspected of generating plausible but unsupported content. It also records how many human annotators agreed on reviewed records, and what sampling method was used to select records for review. This is the infrastructure needed to monitor whether extraction quality is improving or degrading as the model and prompts change over time.

"evaluation_metadata": {
  "batch_id": "batch run identifier",
  "ground_truth_available": true | false,
  "field_accuracy_scores": {
    "field_path": 0.0–1.0
  },
  "suspected_hallucination_fields": ["field_path"],
  "inter_annotator_agreement": 0.0–1.0,
  "review_sampling_method": "random" | "stratified"
                           | "low_confidence" | "full"
}

Processing Metadata

Revised — paradata
What this field does

Records how and when a record was produced — which model was used, which version of the pipeline, and when it ran. In v4 three things are added. First, a prompt_template_version field records exactly which instructions were given to the AI at extraction time, so that if the prompts change, we can identify which records were produced under which instructions. Second, a confidence_calibration_method field records whether the model's self-reported confidence scores have been adjusted — which matters because AI models are reliably overconfident, especially for obscure historical figures. Third, a modification_history array creates a permanent log of every change made to the record from first extraction through human review — who changed what, when, and why. This is what archival scholars call paradata: documentation of the process by which a record was created, not just the record itself.

"processing_metadata": {
  "model_id": "model identifier string",
  "prompt_template_version": "semantic version",
  "processed_at": "ISO 8601 datetime",
  "confidence_calibration_method": "none" | "temperature_scaling"
                                  | "platt_scaling" | "isotonic_regression",
  "modification_history": [
    {
      "timestamp": "ISO 8601 datetime",
      "agent": "model id or reviewer initials",
      "field_changed": "field path",
      "previous_value": "old value",
      "reason": "free text"
    }
  ]
}
"processing_metadata": {

Shared Definitions

$defs — building blocks

Five reusable structures that appear throughout the schema via references. Changing a definition here automatically updates every field that uses it.

What this definition does

A small structured block that attaches to any extracted field to record what kind of uncertainty affected it. In v3, all uncertainty was bundled into a single free-text notes array at the bottom of the record — which is useful for human readers but cannot be processed by software. In v4 each field carries its own typed uncertainty record. The uncertainty_type distinguishes nine different situations: a value read clearly from the text (precise); a value that is roughly right but not exact (approximate); a value the model inferred from context rather than read directly (inferred); a value that sources disagree on (contested); and four specific kinds of ambiguity — transcription problems, date format ambiguity (is "5/6/43" May or June?), name disambiguation, and illegibility. The uncertainty_class distinguishes between uncertainty that is irreducible (the ink is simply too faded to read) and uncertainty that could be resolved with more research. Both the raw model confidence and a separately calibrated confidence figure are stored, along with alternative values the model considered.

{
  "uncertainty_type": "precise" | "approximate" | "inferred" | "contested"
                     | "unknown" | "transcription_ambiguity"
                     | "date_format_ambiguity"
                     | "entity_disambiguation_ambiguity" | "illegibility",
  "uncertainty_class": "aleatoric" | "epistemic" | "unknown",
  "evidence_basis": "explicit_text" | "rubber_stamp" | "handwritten_annotation"
               | "contextual_inference" | "cross_reference"
               | "external_authority" | "model_generation" | "unknown",
  "source_region": "description of image region, e.g. 'top-right stamp'",
  "raw_confidence": 0.0–1.0,
  "calibrated_confidence": 0.0–1.0,
  "alternative_values": [
    { "value": "other plausible reading", "relative_confidence": 0.0–1.0 }
  ]
}

// Situation: name clearly printed in typed caption, no ambiguity

What this definition does

A small record of where a specific piece of extracted information came from: which part of the image it was drawn from, whether it was read directly from the text or inferred, who or what produced it (the model or a human reviewer), and when. If a human reviewer later corrects the value, the original provenance is preserved and a new provenance record is added. This follows the W3C PROV-O standard for provenance on the web, and addresses the archival principle that we should always be able to trace how a factual claim entered a record.

What this definition does

A date-range structure following the CIDOC-CRM museum standard for representing time. Rather than a single ISO-8601 date string, it stores four bounding dates: the earliest and latest possible start of the period, and the earliest and latest possible end. A human-readable display date is stored separately. This means a date like "circa spring 1943" can be recorded as a range spanning March to June 1943, rather than being forced into a precise point date or reduced to an ambiguity flag. The definition is used in four places: dates, events, article.publication_timespan, and stamps.date_timespan.

"timespan": {
  "begin_of_the_begin": "ISO 8601 — earliest possible start",
  "end_of_the_begin":   "ISO 8601 — latest possible start",
  "begin_of_the_end":   "ISO 8601 — earliest possible end",
  "end_of_the_end":     "ISO 8601 — latest possible end",
  "display_date":        "human-readable label"
}
('// "circa spring 1936" — known to be spring,\n// year confirmed from stamp, exact day unknown\n"timespan": {\n  "begin_of_the_begin": "1936-03-01",\n  "end_of_the_begin":   "1936-03-01",\n  "begin_of_the_end":   "1936-05-31",\n  "end_of_the_end":     "1936-05-31",\n  "display_date":        "Spring 1936"\n}',)
// Precise single date — stamp clearly reads "19 Jan 1936"
"timespan": {
  "begin_of_the_begin": "1936-01-19",
  "end_of_the_begin":   "1936-01-19",
  "begin_of_the_end":   "1936-01-19",
  "end_of_the_end":     "1936-01-19",
  "display_date":        "19 January 1936"
}
